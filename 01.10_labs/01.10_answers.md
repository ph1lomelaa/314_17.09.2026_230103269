### A. Baseline and maximum-thread runtime

The single-thread baseline was **T1 = 1.3028 seconds**. The runtime with the maximum available thread count was **Tmax = 0.2456 seconds using 10 threads**, giving a speedup of **5.31x**. The fastest result was obtained with 8 threads: **0.2144 seconds** and **6.08x speedup**.

### B. Why is the JIT warm-up required?

Numba compiles the function into native machine code during its first execution. Without the warm-up call, the first measurement would include both compilation time and computation time. Calling `monte_carlo_pi(10_000)` before the benchmark completes JIT compilation in advance, so the recorded results measure only the execution time and allow a fair comparison between thread counts.

### C. Parallel efficiency

Parallel efficiency did not remain at 100%. It was 99.4% with 2 threads and 98.8% with 4 threads, but decreased to 76.0% with 8 threads and 53.1% with 10 threads.

Parallel execution introduces scheduling, synchronization, random-number generation, and reduction overhead. Threads also compete for cache and memory resources. The Apple M4 contains four performance cores and six efficiency cores, so all cores do not have identical performance. When all 10 cores are active, the slower efficiency cores and additional scheduling overhead limit scaling. This explains why 8 threads completed the benchmark faster than 10 threads.

### D. Reduction of `inside_circle`

Numba recognizes `inside_circle` as a reduction variable inside the `prange` loop. Each worker maintains a private partial count, and the partial results are added together after the parallel loop finishes. This is equivalent to the OpenMP construct:

```c
reduction(+:inside_circle)
```

Therefore, `inside_circle += 1` does not create a race condition or corrupt the result.

## Challenge 2: Load Imbalance and Dynamic Scheduling

### Benchmark results

```text
Row-Parallel Render Time:    1.590 s
Column-Parallel Render Time: 1.677 s
Saved image: mandelbrot_output.png
```

### A. Row versus column decomposition

The row-parallel version was faster. It completed in 1.590 seconds, while the column-parallel version required 1.677 seconds. The row version was approximately **5.2% faster**:

```text
(1.677 - 1.590) / 1.677 * 100% = 5.2%
```

The row-parallel version benefits from sequential memory access because NumPy stores two-dimensional arrays in row-major order.

### B. C-contiguous layout and CPU cache lines

In a C-contiguous NumPy array, elements in the same row are adjacent in memory. In the row-parallel version, the inner loop changes the column index, so writes to `img[r, c]` access consecutive addresses. One cache line contains several values that are used immediately, producing good spatial locality.

In the column-parallel version, the inner loop changes the row index while the column stays fixed. Consecutive writes are separated by an entire row in memory. This strided access uses cache lines less efficiently and produces more cache misses and memory traffic. Therefore, the row-parallel version is faster.

### C. Load imbalance and dynamic scheduling

Mandelbrot pixels require different amounts of computation. Points outside the set may escape after only 2-3 iterations, while points inside the set run all 1000 iterations. A thread assigned the top 20% of rows may finish quickly, while a thread assigned the center 20% may receive many expensive pixels and continue working much longer.

With static scheduling, the first thread becomes idle while the second thread is still busy, and the total runtime is determined by the slowest thread. Dynamic scheduling divides the work into smaller chunks. When a thread finishes one chunk, it requests another one. This distributes expensive and inexpensive regions more evenly and reduces idle time.

## Challenge 3: Stencil Computation and Memory Bandwidth

### A. Float64 benchmark

```text
Heat Diffusion Complete: 0.206 s
Throughput: 3281.37 Megacells/sec
```

The benchmark runtime was **0.206 seconds**, and the throughput was **3281.37 Megacells/second**.

### B. Float32 benchmark and comparison

After changing the array precision from `np.float64` to `np.float32`, the result was:

```text
Heat Diffusion Complete: 0.098 s
Throughput: 6907.02 Megacells/sec
```

The runtime improvement factor was:

```text
0.206 / 0.098 = 2.10x
```

Thus, the `float32` version was approximately **2.10 times faster**. A `float64` value occupies 8 bytes, while a `float32` value occupies 4 bytes. The smaller precision approximately halves the amount of data transferred between RAM, cache, and the CPU and allows more values to fit in cache.

The stencil performs relatively few arithmetic operations per value loaded from memory, so it is limited primarily by memory movement rather than arithmetic capability. Reducing the memory footprint therefore improves stencil throughput significantly.

### C. Memory Roofline Model

The heat stencil has low arithmetic intensity: each cell update loads several neighboring values but performs only a small number of arithmetic operations. Its performance is therefore limited by memory bandwidth.

Adding cores initially increases performance because more cells can be processed simultaneously. However, once the available memory bandwidth is saturated, additional cores cannot receive data any faster. The cores compete for the same memory bus and spend more time waiting for data. Therefore, doubling the number of CPU cores does not produce a 2x speedup after the memory-bandwidth ceiling has been reached.
